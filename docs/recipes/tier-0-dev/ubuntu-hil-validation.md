Run the repository-owned Tier 0 HiL processes on two Ubuntu hosts and return the evidence needed to complete IL and RL acceptance. The simulator workstation runs Isaac. The separate target host runs policy inference. Neither process connects to a physical robot.

## Validation Outcome

Complete these acceptance runs:

| Run | Simulator workstation | Target policy host | Required local artifacts |
|-----|-----------------------|--------------------|--------------------------|
| UR10e ACT | Isaac Sim with your matching UR10e task scene | LeRobot 0.6 ACT process | Scene USD, scene config, matching ACT policy |
| Anymal-C JIT | Isaac Lab `Isaac-Velocity-Rough-Anymal-C-v0` | TorchScript process | `policy.pt`, generated `policy_io.json` |

A same-machine loopback run is useful for debugging but does not complete HiL acceptance. Final evidence requires distinct hostnames.

Transfer or clone the same commit on the simulator workstation. The policy-host image can be built there and transferred to the target host.

Record the source revision:

```bash
git rev-parse HEAD | tee outputs/hil/source-commit.txt
```

### Resources That Stay Outside the Repository

| Resource | Why it stays external | Where to obtain it |
|----------|-----------------------|--------------------|
| Task-matched UR10e scene USD | The repository does not own your task scene or redistribution rights | Export the Isaac scene used to collect or model the policy's training data |
| Processor-format ACT policy | Task-specific trained weights can be large or restricted | Local LeRobot training output or one exact Azure Machine Learning model version |
| Anymal-C JIT policy | Task-specific trained artifact | Export a matching local, OSMO, or Azure Machine Learning checkpoint |
| NVIDIA driver and container runtime | Host-level software | NVIDIA driver download and NVIDIA Container Toolkit documentation |
| NGC access | Credential and account state | NVIDIA NGC account and API key page |
| Host/network details | Environment-specific | Your two Ubuntu systems and directly reachable LAN |
| HiL logs and results | Run-specific evidence | Generated by the commands in this guide |

Do not commit credentials, generated scene files with unverified redistribution rights, trained weights, hostnames, IP addresses, or run outputs.

## Hardware and Host Requirements

### Simulator Workstation

Use an x86_64 Ubuntu 24.04 workstation. Isaac Sim 5.1 lists 32 GB RAM, 50 GB SSD, an RTX 4080-class GPU, 16 GB VRAM, and Linux driver 580.65.06 as its minimum tested x86_64 configuration. Isaac Lab workloads can require more memory.

The workstation needs:

* Docker Engine
* NVIDIA driver compatible with the installed GPU
* NVIDIA Container Toolkit configured for Docker
* NVIDIA NGC access to the pinned Isaac Lab image
* Internet access for initial image and Isaac asset retrieval
* The repository checkout and local artifacts

Official references:

* [Isaac Sim 5.1 requirements](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/requirements.html)
* [Isaac Sim container installation](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/install_container.html)
* [NVIDIA Container Toolkit installation](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)
* [Isaac Sim ROS 2 setup](https://docs.isaacsim.omniverse.nvidia.com/5.1.0/installation/install_ros.html)
* [NVIDIA NGC API key setup](https://org.ngc.nvidia.com/setup/api-key)

### Target Policy Host

Use a second x86_64 Linux host reachable from the simulator workstation. Ubuntu 24.04 is the supported baseline. It needs Docker Engine and enough CPU/RAM for the selected ACT or JIT policy. It does not need an NVIDIA GPU or Isaac installation.

Both hosts must be on a network that permits ROS 2 DDS discovery and traffic. The simplest setup is the same trusted layer-2 LAN with Docker host networking and the same `ROS_DOMAIN_ID`.

## Install Host Software

Install Docker Engine on both hosts by following [Docker Engine on Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Complete the Linux post-install step so the validation user can run Docker without `sudo`, then verify:

```bash
docker version
docker run --rm hello-world
```

Install the NVIDIA driver and NVIDIA Container Toolkit on the simulator workstation only. Use the driver recommended for the installed RTX GPU and the Isaac Sim requirements. Configure Docker after installing the toolkit:

```bash
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

Create an NVIDIA NGC account, request access to the Isaac Lab container when required by your organization, and create an API key from the NGC setup page. Keep the API key out of repository files and command transcripts.

When policies are registered in Azure Machine Learning, install Azure CLI `>=2.38.0` and the current Machine Learning extension on the host that will materialize them:

```bash
curl -sL https://aka.ms/InstallAzureCLIDeb | sudo bash
az extension add -n ml -y
az login
az version
az ml -h
```

Use [Install and set up the Azure Machine Learning CLI v2](https://learn.microsoft.com/azure/machine-learning/how-to-configure-cli?view=azureml-api-2) and the [`az ml model download` reference](https://learn.microsoft.com/cli/azure/ml/model?view=azure-cli-latest#az-ml-model-download) when your workspace or registry requires different context options.

## Prepare the Simulator Workstation

### Verify GPU Containers

```bash
nvidia-smi

docker run --rm --gpus all ubuntu:24.04 nvidia-smi
```

If the second command fails, configure the NVIDIA Container Toolkit before continuing:

```bash
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker
```

### Pull the Pinned Isaac Lab Image

Authenticate to NGC in a terminal without recording the API key in a file or shell history. Use `$oauthtoken` as the literal username and the NGC API key as the password:

```bash
docker login nvcr.io --username '$oauthtoken'

docker pull \
  nvcr.io/nvidia/isaac-lab:2.3.2@sha256:388dbc806f48359a964cb9f807feb226da95d0a107f470fdcad9780ea10fe6f2
```

Create the output directories:

```bash
mkdir -p outputs/hil/{host-evidence,ur10e-001,anymal-c-001}
```

### Build and Transfer the Policy Image

Build on either x86_64 host:

```bash
docker build --platform linux/amd64 \
  --file evaluation/hil/docker/Dockerfile.policy-host \
  --tag physical-ai-hil-policy-host:local \
  .
```

When the target host does not have the repository checkout, transfer the image:

```bash
docker save physical-ai-hil-policy-host:local \
  | gzip > outputs/hil/physical-ai-hil-policy-host.tar.gz

scp outputs/hil/physical-ai-hil-policy-host.tar.gz <target-host>:/tmp/
```

On the target host:

```bash
gzip -dc /tmp/physical-ai-hil-policy-host.tar.gz | docker load
```

## Gather the UR10e IL Artifacts

### Scene

The Isaac Lab 2.3.2 asset configuration references the official UR10e robot at:

```text
${ISAAC_NUCLEUS_DIR}/Robots/UniversalRobots/ur10e/ur10e.usd
```

This is a robot asset, not a task scene. Use Isaac Sim to compose or export the actual scene that matches the ACT training data. The saved stage must contain:

* One six-joint UR10e articulation
* Joint names in the canonical order from the config template
* One RGB camera at the same viewpoint used by training
* RGB output at `480x848`
* The task objects, lighting, reset pose, and control cadence used by training

Save the composed scene under a local directory such as `~/hil-assets/ur10e/scene.usd`. Record the articulation and camera prim paths from the Stage tree.

Copy and edit the configuration:

```bash
mkdir -p ~/hil-assets/ur10e
cp evaluation/hil/config/local-lerobot-ur10e.json \
  ~/hil-assets/ur10e/hil-config.json
```

Set `usd_path` to the in-container mounted path, for example `/workspace/scenes/scene.usd`. Set `articulation_prim_path` and `camera_prim_path` to the exact Stage paths. Keep `steps` synchronized with the target-host `--steps` value.

### ACT Policy

Use a processor-format LeRobot 0.6 checkpoint trained from data matching that scene. A local training run normally produces:

```text
outputs/train/<job>/checkpoints/last/pretrained_model/
```

The directory must contain at least:

```text
config.json
model.safetensors
policy_preprocessor.json
policy_postprocessor.json
```

For an Azure Machine Learning model, materialize one exact version before the run:

```bash
az ml model download \
  --name <model-name> \
  --version <model-version> \
  --download-path ~/hil-assets/act-policy \
  --resource-group <resource-group> \
  --workspace-name <workspace-name>
```

Inspect the downloaded directory and select the directory containing the four required files. Do not use the public ALOHA policy with this UR10e scene.

Copy that complete directory to the target host:

```bash
ssh <target-host> 'mkdir -p ~/hil-assets/act-policy'

scp -r ~/hil-assets/act-policy/<checkpoint-dir> \
  <target-host>:~/hil-assets/act-policy/
```

## Gather the Anymal-C RL Artifacts

### JIT Policy

Use a checkpoint trained for exactly `Isaac-Velocity-Rough-Anymal-C-v0`. Local RSL-RL runs commonly write `model_*.pt` under their run directory. Cloud or OSMO jobs mirror checkpoints through the job output and can register them in Azure Machine Learning.

The repository's Anymal-C RSL-RL configuration disables actor observation normalization. For that configuration, export only JIT into a local artifact directory:

```bash
mkdir -p ~/hil-assets/anymal-c

uv run python training/packaging/scripts/export_policy.py \
  --checkpoint <matching-model-checkpoint.pt> \
  --output-dir ~/hil-assets/anymal-c \
  --no-onnx
```

The command writes `policy.pt`. For an exact registered model version, download the model first with `az ml model download`, then point `--checkpoint` to its matching training checkpoint.

Do not use this standalone exporter when the training configuration enabled actor or student observation normalization. In that case, load the checkpoint with the matching Isaac Lab runner and use Isaac Lab's native `export_policy_as_jit` path so the normalizer is embedded. Keep the exported `policy.pt` with the task configuration used to generate its descriptor.

### Generate `policy_io.json`

Run the repository generator in the pinned Isaac Lab image. It creates the live Anymal-C environment, reads manager term order and shapes, checks the JIT input/output dimensions, and writes the sidecar beside `policy.pt`.

```bash
docker run --rm --gpus all --network host \
  --env ACCEPT_EULA=Y \
  --env PRIVACY_CONSENT=Y \
  --env NVIDIA_DRIVER_CAPABILITIES=all \
  --env PYTHONPATH=/workspace/physical-ai-toolchain \
  --volume "$PWD":/workspace/physical-ai-toolchain \
  --volume "$HOME/hil-assets/anymal-c":/policy \
  --workdir /workspace/physical-ai-toolchain \
  nvcr.io/nvidia/isaac-lab:2.3.2@sha256:388dbc806f48359a964cb9f807feb226da95d0a107f470fdcad9780ea10fe6f2 \
  /workspace/isaaclab/isaaclab.sh -p \
    evaluation/hil/scripts/generate-policy-io.py \
    --policy-path /policy/policy.pt \
    --output /policy/policy_io.json \
    --device cuda:0
```

Copy `policy.pt` and `policy_io.json` together to the target host:

```bash
ssh <target-host> 'mkdir -p ~/hil-assets/anymal-c'

scp ~/hil-assets/anymal-c/{policy.pt,policy_io.json} \
  <target-host>:~/hil-assets/anymal-c/
```

## Record Host Evidence

On the simulator workstation:

```bash
{
  hostname
  uname -m
  nvidia-smi --query-gpu=name,driver_version,memory.total --format=csv,noheader
  git rev-parse HEAD
} | tee outputs/hil/host-evidence/simulator.txt
```

On the target host:

```bash
mkdir -p ~/hil-evidence
{
  hostname
  uname -m
  docker image inspect physical-ai-hil-policy-host:local \
    --format '{{.Id}} {{.Architecture}}'
} | tee ~/hil-evidence/policy-host.txt
```

The hostnames must differ for final HiL acceptance.

## Verify ROS 2 Reachability

Choose one domain ID and use it for every command:

```bash
export ROS_DOMAIN_ID=42
export ROS_LOCALHOST_ONLY=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
```

Start either policy container on the target host. While it waits for observations, run this in another target-host terminal:

```bash
docker run --rm --network host \
  --env ROS_DOMAIN_ID=42 \
  --env ROS_LOCALHOST_ONLY=0 \
  --env RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
  physical-ai-hil-policy-host:local \
  ros2 topic list
```

After the simulator starts, the run-specific `/hil/...` topics must appear. If they do not, confirm both containers use `--network host`, both use the same domain ID, multicast is permitted, and host firewalls allow ROS 2 DDS traffic.

## Optional Same-Machine Smoke Test

Run both containers on the simulator workstation to debug image, topic, scene, and descriptor issues. This does not complete HiL acceptance because both commands share one hostname.

Use the same commands as the final run, but mount the policy artifacts from the simulator workstation and start the policy container there.

## Run the UR10e IL Acceptance

Start the target process first on the target host:

```bash
set -o pipefail
mkdir -p ~/hil-evidence/ur10e-001

{
  hostname
  uname -m
  docker run --rm --network host \
    --env ROS_DOMAIN_ID=42 \
    --env ROS_LOCALHOST_ONLY=0 \
    --env RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
    --volume "$HOME/hil-assets/act-policy/<checkpoint-dir>":/policy:ro \
    physical-ai-hil-policy-host:local \
    python evaluation/hil/scripts/run-local-lerobot-policy.py \
      --policy-path /policy \
      --device cpu \
      --steps 100 \
      --run-id ur10e-001
} 2>&1 | tee ~/hil-evidence/ur10e-001/policy-host.log
```

Start the simulator process on the simulator workstation:

```bash
set -o pipefail

{
  hostname
  uname -m
  docker run --rm --gpus all --network host \
    --env ACCEPT_EULA=Y \
    --env PRIVACY_CONSENT=Y \
    --env NVIDIA_DRIVER_CAPABILITIES=all \
    --env PYTHONPATH=/workspace/physical-ai-toolchain \
    --env ROS_DOMAIN_ID=42 \
    --env ROS_LOCALHOST_ONLY=0 \
    --env RMW_IMPLEMENTATION=rmw_fastrtps_cpp \
    --volume "$PWD":/workspace/physical-ai-toolchain \
    --volume "$HOME/hil-assets/ur10e":/workspace/scenes:ro \
    --workdir /workspace/physical-ai-toolchain \
    nvcr.io/nvidia/isaac-lab:2.3.2@sha256:388dbc806f48359a964cb9f807feb226da95d0a107f470fdcad9780ea10fe6f2 \
    /workspace/isaaclab/isaaclab.sh -p \
      evaluation/hil/scripts/run-local-lerobot-sim.py \
      --config /workspace/scenes/hil-config.json \
      --policy-id <policy-name-and-version> \
      --output-dir outputs/hil/ur10e-001 \
      --run-id ur10e-001 \
      --headless --enable_cameras
} 2>&1 | tee outputs/hil/ur10e-001/simulator.log
```

Both commands must exit zero. Verify the result:

```bash
jq -e '
  .framework == "lerobot-act" and
  .requested_steps == .completed_steps and
  .timing.round_trip_latency_ms.sample_count == .completed_steps and
  .outcomes.termination_reason == "step-limit"
' outputs/hil/ur10e-001/summary.json
```

## Failure Routing

| Failure | Action |
|---------|--------|
| Isaac image pull denied | Authenticate to NGC and confirm access to the pinned Isaac Lab image |
| GPU unavailable in container | Recheck the host driver, NVIDIA Container Toolkit, Docker runtime configuration, and `NVIDIA_DRIVER_CAPABILITIES=all` |
| Policy host times out waiting | Start the simulator and inspect run-specific topics |
| Simulator times out waiting | Confirm matching domain/run IDs, host networking, DDS reachability, and target process logs |
| UR10e prim or joint mismatch | Correct the scene config from the Isaac Stage tree; do not substitute another prim |
| Camera shape or encoding mismatch | Recreate the training-matched RGB camera at `480x848` |
| ACT loader rejects checkpoint | Use a complete LeRobot 0.6 processor-format directory |
| Descriptor generation fails | Use the exact Anymal-C training task and matching JIT policy |
| Descriptor/runtime term mismatch | Regenerate `policy_io.json` with the same pinned Isaac Lab image and policy |
| Same hostname in both records | Treat the run as development smoke only and repeat on distinct hosts |

Do not add retries, local-policy fallback, alternate task selection, or physical robot endpoints to work around a failed acceptance run.
